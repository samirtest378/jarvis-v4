# Security Policy

Thank you for helping improve the security of this project. We take security seriously and appreciate the efforts of researchers and community members who responsibly disclose vulnerabilities.

This document explains which versions are supported, how to report security issues, what you can expect after submitting a report, and how vulnerabilities are handled.

---

# Supported Versions

Only actively maintained releases receive security updates.

| Version | Supported |
|----------|-----------|
| Latest Stable Release | ✅ |
| Previous Stable Release | ✅ (Critical fixes only) |
| Development / Beta | ⚠️ Best effort |
| Older Releases | ❌ |

If you are using an unsupported version, please upgrade to the latest release before reporting a security issue.

---

# Reporting a Vulnerability

## Please Do Not Report Security Issues Publicly

To protect users, please **do not create a public GitHub Issue** for security vulnerabilities.

Instead, report vulnerabilities privately using one of the following methods:

- **GitHub Security Advisories (Preferred)**, if available.
- **Email:** security@example.com

Replace the email address above with the official project security contact.

---

# What to Include

Providing detailed information helps us investigate and resolve issues more quickly.

Please include:

- A clear description of the vulnerability
- The affected version(s)
- Steps to reproduce the issue
- Proof of concept (if available)
- Expected behavior
- Actual behavior
- Potential impact
- Relevant logs or screenshots (if applicable)
- Possible mitigation or suggested fix (optional)

Reports containing sufficient technical details can usually be processed much faster.

---

# Response Process

After receiving your report, we will:

1. Confirm receipt of the report.
2. Review and validate the vulnerability.
3. Assess its severity and potential impact.
4. Develop and test a fix.
5. Release a security update if necessary.
6. Notify affected users through the appropriate release notes or security advisory.

---

# Expected Response Times

We aim for the following response times:

| Action | Target Time |
|---------|-------------|
| Acknowledgement | Within 48 hours |
| Initial Assessment | Within 7 days |
| Status Updates | At least every 7 days |
| Security Fix | As soon as reasonably possible |

Complex vulnerabilities may require additional investigation and testing.

---

# Responsible Disclosure

We kindly ask that you:

- Give us reasonable time to investigate and fix the issue.
- Avoid publicly disclosing vulnerabilities before a fix is available.
- Avoid sharing exploit code that could put users at risk.
- Work with us during the disclosure process.

Once a fix has been released, coordinated public disclosure is welcome.

---

# Severity Assessment

Security reports are evaluated based on factors such as:

- Impact on confidentiality
- Impact on integrity
- Impact on availability
- Ease of exploitation
- Required privileges
- User interaction
- Overall risk to users

Not every reported issue will be classified as a security vulnerability.

---

# Out of Scope

The following generally do **not** qualify as security vulnerabilities:

- Requests for new security features
- Missing best-practice headers without practical impact
- Social engineering attacks
- Physical access attacks
- Vulnerabilities in unsupported versions
- Issues caused by third-party software outside this project's control
- Denial-of-service attacks requiring unrealistic resources
- Reports without reproducible evidence

---

# Security Updates

Security fixes are released as soon as they have been sufficiently tested.

Critical vulnerabilities may receive an out-of-band release outside the normal release schedule.

We strongly recommend always using the latest stable version.

---

# Dependency Security

We regularly monitor project dependencies for known vulnerabilities.

When security issues are discovered in third-party dependencies, we aim to:

- Update affected packages
- Replace unsupported dependencies
- Publish patched releases when necessary

---

# Supported Platforms

Security updates are provided only for officially supported operating systems and environments.

Issues caused by unsupported operating systems, unofficial modifications, or heavily customized deployments may not be addressed.

---

With your permission, we may acknowledge your contribution in our release notes or security advisories.
